## 5.1 为什么需要标准化笔记

原始文件不能直接作为 AI 知识库的主要内容，原因包括：

1. **原始文件太长**  
   很多 PDF、Word、PPT、Excel 文件内容较长，不利于快速阅读和检索。

2. **格式不统一**  
   原始资料可能包括 PDF、Word、Excel、PPT、图片、录音转写文本等，不同格式难以统一处理。

3. **无法形成清晰知识图谱**  
   原始文件中包含大量无效信息、重复信息和背景信息，直接进入知识库后容易造成知识图谱混乱。

4. **检索困难**  
   AI 检索时可能遗漏重点，或者检索到大量不相关内容。

5. **不方便追溯来源**  
   如果没有标准化整理，后续很难知道某个观点、数据或结论来自哪份原始材料。

因此，需要把重要原始材料整理成标准化 Markdown 笔记。

不过，正如 [[04-文件存储设计]] 中所说：

> 写 Markdown 文件不应该成为用户的额外负担。

更合理的方式是：

1. 不是所有原始文件都必须立刻整理成 Markdown；
2. 是否创建 Markdown 笔记，要从实际业务需求出发；
3. 标准化笔记应优先覆盖重要项目、重要结论、重要方法论和高频使用资料；
4. Markdown 笔记的生成应尽量借助智能体完成，减少人工整理成本。

---

## 5.2 标准笔记的基本结构

系统中的文件可以有多种格式，但正式知识笔记建议统一使用 Markdown 文件。

一篇标准 Markdown 笔记通常包括两部分：

```text
Frontmatter
正文内容
```

其中：

1. **Frontmatter**  
   位于 Markdown 文件开头，用于记录结构化元信息。

2. **正文内容**  
   用于记录摘要、分析、判断、数据、证据、结论等内容。

---

## 5.3 什么是 Frontmatter

Frontmatter 是放在 Markdown 文件开头的一段结构化信息，通常使用 YAML 格式。

它的作用是告诉系统：

- 这篇笔记是什么类型；
- 创建时间是什么；
- 最近更新时间是什么；
- 来源文件是什么；
- 使用了哪些标签；
- 当前状态是什么；
- 敏感等级是什么；
- 修改记录是什么。

简单来说，Frontmatter 是一篇笔记的“元信息”。

它不直接承载正文内容，但可以帮助 Obsidian、智能体和知识库系统更好地理解、检索和管理这篇笔记。

---

## 5.4 标准笔记示例

```yaml
---
title: "元科医疗 — 投资建议书"
type: analysis
created: 2026-04-20
updated: 2026-04-20
sources:
  - "原始材料/元科医疗/上会PPT/元科医疗_投资建议书_20260420.docx"
  - "原始材料/元科医疗/访谈纪要/程总到访协立投资会议纪要_20260415.md"
changelog:
  - date: "2026-04-20"
    change: "首次创建"
tags:
  - 行业=医疗器械
  - 阶段=A轮
  - 风险=技术风险
  - 财务=亏损
status: published
sensitivity: 内部
---
```

正文部分示例：

```markdown
# 元科医疗 — 投资建议书

> 项目代号：元科  
> 投资方：协立投资  
> 上会日期：2026-04-20

## 一、项目概述

（公司一句话定位 + 投资亮点）

## 二、关键数据

（财务尽调核心数据）

## 三、风险评估

（基于标签标记的风险类型）

## 四、投资建议

（领投 / 跟投 / 继续观察 / 放弃）

## 五、原文出处

- 原始材料：[[原始材料/元科医疗/元科医疗_投资建议书_20260420.docx]]
- 会议纪要：[[原始材料/元科医疗/访谈纪要/2026-04-XX_元科医疗程总到访协立投资_会议纪要.md]]
```

## 5.5 Frontmatter 必填字段

| 字段 | 是否必填 | 说明 | 示例 |
|---|---|---|---|
| `title` | 是 | 笔记标题 | `"元科医疗 — 投资建议书"` |
| `type` | 是 | 笔记类型 | `"analysis"` |
| `created` | 是 | 创建日期 | `"2026-04-20"` |
| `updated` | 是 | 最近更新日期 | `"2026-04-20"` |
| `sources` | 是 | 引用的原始文件 | `["原始材料/.../文件名"]` |
| `changelog` | 是 | 修改记录 | `[{date: "2026-04-20", change: "首次创建"}]` |
| `tags` | 是 | 标签 | `["行业=医疗器械", "阶段=A轮"]` |
| `status` | 是 | 当前状态 | `"published"` |
| `sensitivity` | 是 | 敏感等级 | `"内部"` |

---

## 5.6 字段说明

### 5.6.1 title

`title` 是笔记标题。

建议标题清晰、具体，能够直接反映笔记内容。

示例：

```yaml
title: "元科医疗 — 投资建议书"
```

不推荐：

```yaml
title: "项目分析"
```

推荐：

```yaml
title: "元科医疗 — A轮投资建议书"
```

---

### 5.6.2 type

`type` 是笔记类型，用来说明这篇笔记属于哪一类知识。

示例：

```yaml
type: analysis
```

常见类型包括：

| 类型 | 说明 | 示例 |
|---|---|---|
| `summary` | 事实摘要，例如访谈纪要总结 | `"某专家访谈纪要总结"` |
| `analysis` | 分析判断，例如投资建议书 | `"元科医疗投资建议书"` |
| `idea` | 方法论、灵感、复盘 | `"早期生物医药估值方法论"` |
| `index` | 索引页 | `"投前项目索引"` |
| `topic` | 主题聚合页 | `"GLP-1赛道全景"` |

---

### 5.6.3 created

`created` 是笔记创建日期。

示例：

```yaml
created: 2026-04-20
```

---

### 5.6.4 updated

`updated` 是最近更新日期。

每次对笔记进行重要修改后，都应更新该字段。

示例：

```yaml
updated: 2026-04-25
```

---

### 5.6.5 sources

`sources` 用于记录这篇笔记引用或依据的原始材料。

示例：

```yaml
sources:
  - "原始材料/元科医疗/上会PPT/元科医疗_投资建议书_20260420.docx"
  - "原始材料/元科医疗/访谈纪要/程总到访协立投资会议纪要_20260415.md"
```

该字段非常重要，因为它决定了笔记是否能够追溯来源。

---

### 5.6.6 changelog

`changelog` 用于记录笔记的修改历史。

示例：

```yaml
changelog:
  - date: "2026-04-20"
    change: "首次创建"
  - date: "2026-04-25"
    change: "补充财务数据和风险分析"
```

它可以帮助用户了解：

1. 笔记什么时候创建；
2. 什么时候修改；
3. 修改了什么内容。

---

### 5.6.7 tags

`tags` 用于记录笔记标签。

示例：

```yaml
tags:
  - 行业=医疗器械
  - 阶段=A轮
  - 风险=技术风险
  - 财务=亏损
```

标签的作用是帮助分类、检索和建立知识关联。

---

### 5.6.8 status

`status` 用于表示笔记当前状态。

示例：

```yaml
status: published
```

常见状态包括：

| 状态 | 说明 | 使用场景 |
|---|---|---|
| `draft` | 草稿，未正式发布 | 初稿撰写、内部讨论 |
| `review` | 待评审 | 等待内部评审或修改 |
| `published` | 已发布，可被正式引用 | 投委会材料、正式分析、成熟笔记 |
| `rejected` | 已拒绝 | 已否决项目或不再采用的内容 |
| `archived` | 已归档，作为历史资料保存 | 过期项目、历史记录、已终止项目 |

状态转换可以简化理解为：

```text
draft 草稿
   ↓
review 待评审
   ↓
published 已发布
   ↓
archived 已归档
```

部分内容也可能出现：

```text
draft 草稿 → rejected 已拒绝
```

---

### 5.6.9 sensitivity

`sensitivity` 用于表示笔记敏感等级。

示例：

```yaml
sensitivity: 内部
```

常见敏感等级包括：

| 敏感等级 | 说明 |
|---|---|
| `公开` | 可公开或半公开使用的资料 |
| `内部` | 仅限内部成员使用 |
| `未发布` | 待上会、待披露或尚未正式确认的资料 |
| `机密` | 涉及核心商业秘密、未公开交易信息、关键决策材料 |

---

## 5.7 笔记类型说明

### 5.7.1 summary：事实摘要

`summary` 适合用于对原始资料进行客观总结。

例如：

- 访谈纪要总结；
- 会议纪要摘要；
- 研报摘要；
- 公司 BP 摘要；
- 尽调材料摘要。

特点是：

> 以事实整理为主，尽量少加入主观判断。

---

### 5.7.2 analysis：分析判断

`analysis` 适合用于记录带有判断、推理和结论的笔记。

例如：

- 投资建议书；
- 公司分析报告；
- 风险评估；
- 财务分析；
- 行业投资机会分析。

特点是：

> 不只是总结资料，而是要形成观点和判断。

---

### 5.7.3 idea：方法论与复盘

`idea` 适合用于记录方法论、经验总结、灵感和复盘内容。

例如：

- 早期生物医药估值方法论；
- AI 赛道投资判断框架；
- 某项目失败复盘；
- 尽调问题清单；
- 投后管理经验总结。

特点是：

> 强调可复用性，适合作为长期知识沉淀。

---

### 5.7.4 index：索引页

`index` 适合用于建立导航页面。

例如：

- 投前项目索引；
- 投后项目索引；
- 行业研究索引；
- 公司画像索引；
- 投资关联关系索引。

特点是：

> 主要用于链接其他笔记，帮助用户快速找到内容。

---

### 5.7.5 topic：主题聚合页

`topic` 适合用于聚合跨项目、跨时间、跨资料来源的主题内容。

例如：

- GLP-1 赛道全景；
- 医疗器械出海专题；
- AI 医疗投资机会；
- 创新药支付政策变化；
- 高端制造国产替代专题。

特点是：

> 围绕一个主题，持续汇总多个来源的资料和观点。

---

## 5.8 标签体系

### 5.8.1 标签的作用

标签的作用是帮助系统快速筛选资料。

例如：

```text
查找所有“生物医药 + A轮 + 技术风险”的项目。
```

对于 AI 知识库来说，标签可以帮助智能体更快判断：

1. 这篇笔记属于哪个行业；
2. 项目处于什么阶段；
3. 涉及哪些风险；
4. 财务状况如何；
5. 笔记适合在哪些场景中被调用。

---

### 5.8.2 自由标签的问题

如果大家自由创建标签，会出现：

- `生物医药`
- `医药`
- `医疗健康`
- `生命科学`
- `BioTech`

这些标签可能指向相近内容，但 AI 和搜索系统很难统一识别。

因此，不建议完全自由创建标签。

---

### 5.8.3 解决方案：受控词表

建议使用**受控词表**确保标签一致性。

也就是说，标签应尽量从事先定义好的词表中选择，而不是每个人随意创造。

标签格式建议采用：

```text
维度=标签值
```

例如：

```yaml
tags:
  - 行业=医疗器械
  - 阶段=A轮
  - 风险=技术风险
  - 财务=亏损
```

---

## 5.12 标签使用统计与质量评估

### 5.12.1 使用频率分析

建议定期分析标签使用情况。

| 标签 | 使用次数 | 使用频率 | 建议 |
|---|---:|---:|---|
| 行业=生物医药 | 45 | 25% | 核心标签，保留 |
| 阶段=A轮 | 23 | 13% | 常用标签，保留 |
| 风险=技术风险 | 18 | 10% | 常用标签，保留 |
| 行业=金融科技 | 5 | 3% | 低频，但可保留 |
| 风险=政策风险 | 2 | 1% | 极低频，考虑合并或保留观察 |

---

### 5.12.2 标签质量评估

可以从以下角度评估标签质量：

1. **使用率过低**  
   可能是标签定义不清晰，或业务中很少用到。

2. **使用率过高**  
   可能是标签定义过宽泛，无法形成有效区分。

3. **组合查询少**  
   说明标签之间关联性不强，或者标签没有服务实际检索需求。

4. **新标签申请多**  
   可能说明现有词表不完善，需要扩展。

5. **同义标签过多**  
   说明标签治理不足，需要合并和规范。
