## 4.1 文件存储设计

### 4.1.1 关于文件存储设计的基本理解

用户可能会对“什么时候创建 Markdown 文件”感到困惑。

例如：

- 是否每次录入资料都要创建一个 Markdown 文件？
- 什么情况下需要形成 Markdown 笔记？
- 原始文件和 Markdown 文件之间是什么关系？

我的理解是：**是否创建 Markdown 文件，应该从目的出发，而不是机械规定。**

Markdown 文件的创建，主要是为了满足两类需求：

1. **符合 Obsidian 的使用习惯**  
   有了 Markdown 文件，Obsidian 才能更好地进行分类、引用、双链和知识图谱构建。

2. **符合大模型的处理偏好**  
   相比 PDF、Word、Excel 等原始文件，结构清晰的 Markdown 文档更便于大模型理解、检索、总结和进一步加工。

因此，这一部分没有必要规定“所有资料都必须创建 Markdown 文件”。更合理的做法是：

> 从实际需求出发，判断哪些资料需要知识化、结构化、笔记化。

如果不加区分地为所有资料创建 Markdown 文件，反而可能造成新的混乱。

并且，在实际任务中，为了减轻用户负担， Markdown 文件的创建应大量通过智能体完成。

---

## 4.2 知识库目录分类

知识库目录整体分为两大类：

1. **原始材料**  
   未处理或少量处理的原始文件，例如 PDF、Word、Excel、PPT、图片、录音、会议材料等。

2. **整理后的知识笔记**  
   经过提炼、总结、结构化后的标准化 Markdown 文档。

二者的关系可以理解为：

```text
原始材料 = 证据和资料来源
知识笔记 = 对原始材料的理解、提炼和再组织
```

## 4.4 目录设计原则

### 4.4.1 物理隔离

原始材料和知识笔记应尽量分开存储。

原始材料主要用于保留证据和资料来源，知识笔记主要用于沉淀理解、观点和方法论。

这样可以避免：

- 原始文件和加工后笔记混在一起；
- 后续难以判断资料来源；
- 大模型处理时上下文混乱；
- Obsidian 知识图谱过度杂乱。

---

### 4.4.2 权限分层

不同敏感度的资料应放在不同目录中。

例如：

- 普通行业资料可以开放给较多人访问；
- 投前项目资料应控制访问范围；
- 投后项目资料应按项目权限管理；
- 基金报告、LP 材料、内部制度等应有更高权限。

权限分层的目标是：

> 让需要的人能够访问资料，同时避免不必要的敏感信息扩散。

---

### 4.4.3 分类清晰

目录结构应尽量按照业务类型组织，而不是按照个人习惯随意创建。

例如：

- 投前项目归入 `01_项目中心/投前项目/`
- 投后项目归入 `01_项目中心/投后项目/`
- 行业研究归入 `02_知识与研究/行业研究/`
- 方法论归入 `02_知识与研究/投资方法论/`
- 制度模板归入 `03_运营与导航/制度与模板/`
- 历史资料归入 `04_归档/`

分类清晰后，用户和智能体都更容易找到资料。

---

### 4.4.4 易于维护

目录结构应尽量保持扁平，不要过深。

不推荐：

```text
项目中心/投前/医疗/器械/影像/2026/初筛/某项目/材料/最终版/修改版/
```

更推荐：

```text
01_项目中心/投前项目/某项目/01_原始资料/
```

目录层级过深会带来几个问题：

- 用户不知道文件应该放在哪里；
- 文件路径过长；
- 后期迁移和归档麻烦；
- 智能体检索时更容易混乱。

# 4.5 资料管理规范

## 4.5.1 核心原则

文件存储结构和归档流程的核心是：

> 从需求出发。

不是所有文件都需要立刻整理成 Markdown，也不是所有资料都需要马上进入知识库。

更合理的方式是：

```text
先低摩擦收集原始资料
再由 AI 或人工进行初步整理
最后根据业务需要沉淀为知识笔记
```

---

## 4.5.2 文件归档流程

### 第一步：资料收集

将原始文件直接存入对应分类的原始材料库。

这一阶段的重点是降低录入成本，不要求用户进行复杂整理。

例如：

```text
01_项目中心/投前项目/元科医疗/01_原始资料/
```

可以存放：

- BP；
- 尽调材料；
- 财务表格；
- 会议纪要；
- 行业资料；
- 公司官网资料；
- 专家访谈记录；
- 管理层访谈材料。

这一阶段的原则是：

> 先收进来，不要因为整理成本太高而阻碍资料沉淀。

---

### 第二步：智能预处理

通过 AI 扫描新增原始文件，并进行初步处理。

主要包括：

1. 识别文件内容；
2. 规范文件命名；
3. 提取核心摘要；
4. 生成关键词或标签；
5. 形成简短的 Markdown 导读文件。

这个导读文件不一定很长，它的作用是帮助用户和智能体快速理解原始资料。

例如：

```text
某公司BP_导读.md
```

其中可以包括：

```markdown
# 某公司BP导读

## 核心摘要

本文档为某公司融资 BP，主要介绍公司业务、核心产品、商业模式、融资需求和未来规划。

## 关键信息

- 公司名称：
- 所属行业：
- 核心产品：
- 融资轮次：
- 融资金额：
- 主要客户：
- 关键风险：

## 原始文件

- [[某公司BP.pdf]]
```

---

### 第三步：按需知识化

根据业务需求创建 Markdown 笔记，记录核心观点和分析结论。

不是所有原始资料都需要知识化。通常只有以下资料值得进一步整理：

1. 高频使用的资料；
2. 对投资判断有重要影响的资料；
3. 可以复用的方法论；
4. 重要项目的关键材料；
5. 有长期参考价值的行业研究；
6. 需要进入公司画像、行业框架或投研体系的内容。

这一阶段形成的 Markdown 笔记，不只是原文摘要，而是应该包含人的理解和判断。

例如：

```markdown
# 元科医疗_初步投资判断

## 一句话结论

元科医疗是一家处于早期阶段的医疗器械公司，核心看点在于……

## 核心投资逻辑

1. 行业空间：
2. 产品壁垒：
3. 团队能力：
4. 商业化进展：

## 主要风险

1. 注册审批风险；
2. 临床验证风险；
3. 市场推广风险；
4. 同类竞品风险：

## 关键证据

- [[元科医疗BP.pdf]]
- [[元科医疗访谈纪要.md]]
- [[医疗器械行业研究.md]]
```

---

### 第四步：复盘与归档

当项目终止、项目完成、季度结束或资料不再高频使用时，应进行归档。

归档时主要做两件事：

1. **整体迁移项目文件至归档区**  
   保留完整原始资料和过程资料，方便未来追溯。

2. **萃取可复用知识至全局知识库**  
   将有长期价值的经验、方法、判断、行业规律提炼出来，放入知识与研究区。

例如，一个终止项目可以归档到：

```text
04_归档/已终止项目/元科医疗/
```

同时，将其中可复用的内容沉淀为：

```text
02_知识与研究/专题与复盘/医疗器械早期项目失败案例复盘.md
```

这样既保留了项目历史，也沉淀了组织知识。

# 4.6 存储容量规划

## 4.6.1 容量需求估算（单用户）

| 资料类型 | 单项目平均 | 年增长 | 5 年预估 |
|---|---:|---:|---:|
| BP 和尽调材料 | 500MB | 2GB | 10GB |
| 行业研究 | 200MB | 1GB | 5GB |
| 投后跟踪 | 100MB | 500MB | 2.5GB |
| 基金报告 | 50MB | 300MB | 1.5GB |
| 制度规则 | 30MB | 200MB | 1GB |
| **总计** | **880MB** | **4GB** | **20GB** |

> 注：以上只是保守估算。实际容量会受到 PDF 扫描件、音视频资料、图片、模型生成文件、历史版本等因素影响。

---

## 4.6.2 扩展建议

### 1. 预留空间

NAS 至少预留 50% 的空闲空间。

原因是：

- 未来资料增长不可完全预测；
- 文件同步和备份需要临时空间；
- 系统运行也可能产生缓存和中间文件；
- RAID 和快照机制可能占用额外空间。

---

### 2. 定期清理

建议每年清理一次不再需要的文件。

清理对象包括：

- 重复文件；
- 临时文件；
- 无效版本；
- 过期中间稿；
- 已完成项目中的冗余材料。

但清理前应先确认是否已经备份，避免误删重要资料。

---

### 3. 备份策略

重要文件应有备份，尤其是：

- 项目核心资料；
- 投资决策文件；
- 基金报告；
- 投后管理资料；
- 制度文件；
- 公司画像；
- 知识笔记。

建议至少保留一份异地备份，避免单点故障。

---

### 4. 监控预警

建议设置存储空间使用率预警。

例如：

- 使用率超过 70%：提醒关注；
- 使用率超过 80%：准备扩容或清理；
- 使用率超过 90%：立即处理，避免影响系统运行。
